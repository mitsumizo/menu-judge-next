description: Implement a given issue end to end automatically - sub-agent delegation + TDD + parallel review through to PR creation, all in one pass (no manual verification). Use for issues you want finished quickly.
---

## 引数の解釈

`$ARGUMENTS` は **「Issue 番号 [base ブランチ名]」** の形で受け取る（base ブランチは省略可）。

- 例 1: `12` → `ISSUE_NUMBER=12`, `BASE_BRANCH=main`（デフォルト）
- 例 2: `12 feature/phase-3` → `ISSUE_NUMBER=12`, `BASE_BRANCH=feature/phase-3`（フェーズ用ブランチに積む場合）

最初のトークンを `ISSUE_NUMBER`、2 つ目があればそれを `BASE_BRANCH` として扱う。

Issue #$ISSUE_NUMBER を `$BASE_BRANCH` をベースに、**動作確認なしで最後まで**実装してください。

## サブエージェントへの委譲ルール（厳守）

このコマンドは、オーケストレーター（メインのセッション）とサブエージェントの分業で進める。実装とレビューは Agent ツール（`general-purpose`）に委譲し、**`model: "sonnet"` を必ず指定する**（トークン消費を抑えるため）。品質は、段階ごとの検証ゲート（オーケストレーターが自分で再実行する）と再委譲で担保する。

| 工程                                             | 担当                       |
| ------------------------------------------------ | -------------------------- |
| 事前準備（Issue 取得・worktree 作成・環境設定）  | オーケストレーター         |
| 段階 1: lib（TDD）                               | サブエージェント（sonnet） |
| 段階 2: コンポーネント（story の play でテスト） | サブエージェント（sonnet） |
| 段階 3: ページ・Server Action・文言・E2E         | サブエージェント（sonnet） |
| レビュー（観点ごとに並列）                       | サブエージェント（sonnet） |
| 段階ごとの検証・コミット・push・PR 作成          | オーケストレーター         |

変更のない段階はスキップし、委譲もしない。

### 委譲プロンプトに必ず書くこと

サブエージェントは会話の文脈を共有しない。毎回次を含める。

1. **worktree の絶対パス**（すべてのファイル操作とコマンドをこの配下で行うこと）
2. **Issue 番号・本文・受け入れ基準の要約**
3. **前の段階の成果物**（作成・変更したファイル、型定義の場所）
4. **その段階の TDD の進め方と検証コマンド**（下の「実装の順序」の該当部分）
5. **CLAUDE.md を最初に読むこと**（Atomic Design の階層ルール・エラー処理・セキュリティ・テスト方針）
6. **完了条件と報告形式**: テストとビルドの成功を自分で確かめたうえで、変更ファイル一覧・追加したテストケース・未解決事項を返す

### オーケストレーターが自分で行うこと（委譲しない）

- Issue 取得・worktree 作成・環境設定
- **各段階の後の検証ゲート**: サブエージェントの報告をうのみにせず、検証コマンドを自分で再実行してからコミットする
- git commit / push / PR 作成（コミットの粒度を管理するため）
- レビュー観点の選定・結果の集約・修正方針の決定

### エラー時のエスカレーション

- 検証ゲートで失敗したら、エラーログを添えて**同じ段階をもう一度委譲**する
- 2 回の再委譲で解決しない型・ビルドエラーは、`/dev:build-fix` の手順を渡して委譲する
- それでも解決しない場合は**実装を止め**、エラー内容・試した修正・推定原因をまとめてユーザーに報告する（推測での場当たり修正を重ねない）
- 段階ごとの再委譲回数を記録し、完了報告に含める（0 回でも書く）

## 実装手順

### 1. 事前準備

1. **Issue の取得**: `gh issue view $ISSUE_NUMBER` で実装内容と受け入れ基準を把握する。関連する設計書・計画書（`docs/superpowers/`）の該当箇所も読む

2. **worktree 作成**（今のチェックアウトのブランチは切り替えない）

   ```bash
   git fetch origin $BASE_BRANCH
   git worktree add .claude/worktrees/issue-$ISSUE_NUMBER -b feature/issue-$ISSUE_NUMBER origin/$BASE_BRANCH
   ```

   - 同名のブランチがすでにある場合は、未マージのコミットがないか確認してからユーザーに削除の可否を聞く

3. **環境設定**: `.claude/worktrees/issue-$ISSUE_NUMBER` で `npm ci` を実行する
   - verify: `npm run typecheck` が通る

4. **実装計画を Issue に残す（中断対策）**
   - 実施する段階・対象ファイル・受け入れ基準の解釈・フィクスチャへの影響を短くまとめ、**実装を始める前に** `gh issue comment $ISSUE_NUMBER` で記録する
   - 目的: 途中で止まっても、新しいセッションがこのコメントを読めば調査をやり直さずに再開できる

### 2. 実装（TDD + 段階ごとの検証）

#### 事前チェック: テストフィクスチャの影響調査

検証ルールや `Dish` の項目・エラーコードを変える場合は、**実装前に**テストのフィクスチャ・モックデータ（`src/components/**/fixtures.ts`・`src/testing/`・各テストの入力）を横断検索し、影響するデータを先に更新する。

#### 実装の順序（厳守）

各段階はサブエージェントに委譲し、検証はオーケストレーターが行う。**失敗したら次の段階に進まない**。

1. **段階 1: lib**（`src/lib/`）— `/dev:tdd` と `/dev:new-lib` の手順を渡す
   - 検証: `npm run test:unit`（ブラウザ API を使うなら `npm run test:browser` も）と `npm run typecheck`
2. **段階 2: コンポーネント**（atoms → molecules → organisms → templates）— `/dev:new-component` の手順を渡す
   - 検証: `npm run test:storybook` と `npm run typecheck`
3. **段階 3: ページ・Server Action・文言**（`src/app/[locale]/`・`src/messages/`）と必要な E2E（`e2e/`）
   - 検証: `npm run build` と `npm run e2e`

#### TDD のサイクル（各段階のサブエージェントが実施）

```
RED → GREEN → REFACTOR
```

1. **RED**: Issue から必要なテストケースを洗い出し、失敗するテストを先に書く。失敗を確認してから実装する
2. **GREEN**: テストを通す最小限の実装を書く
3. **REFACTOR**: テストを通したまま改善する
4. **品質チェック**: `npm run typecheck` と `npm run lint`

- 実装より先にテストを書く。RED を飛ばさない
- 一度に 1 つのテストケースに集中する

### 3. 段階的なコミット

意味のある単位で小刻みにコミットする。形式は `<type>: <subject>`（英語）。

- テスト追加: `test: Add tests for ...`
- 実装: `feat: Add ...`
- リファクタ: `refactor: ...`

### 4. 並列レビュー（PR 作成前）

すべての実装が終わったら、**観点ごとに分けて、サブエージェントで並列にレビュー**する。

#### Step 1: 変更の分析

```bash
git diff --name-only origin/$BASE_BRANCH
git diff --stat origin/$BASE_BRANCH
git diff origin/$BASE_BRANCH   # 委譲プロンプトに同梱する diff 本文
```

diff 本文はオーケストレーターが**一度だけ**取得し、各レビュアーに配る（レビュアーごとに取り直させない）。

#### Step 2: 観点の選定

今回の変更に**必要な観点だけ**を選ぶ。選ばなかった理由も一言残す（例: `スキップ: i18n（messages とロケール処理の変更なし）`）。

| #   | 観点               | 適用条件                                                                                                | 常時 |
| --- | ------------------ | ------------------------------------------------------------------------------------------------------- | ---- |
| 1   | セキュリティ       | APIキー・画像の受け付け・Claude への送信・Server Action・`next.config.ts` のヘッダー・`proxy.ts` の変更 | -    |
| 2   | アーキテクチャ     | コンポーネントの新規追加、階層をまたぐ変更、`"use client"` の追加                                       | -    |
| 3   | i18n               | `src/messages/`・`src/i18n/`・`proxy.ts`・`useTranslations` を使う箇所の変更                            | -    |
| 4   | パフォーマンス     | 画像処理・`useEffect`・リスト描画・静的生成に関わる変更、依存パッケージの追加                           | -    |
| 5   | テスト品質         | `*.test.ts`・`*.browser.test.ts`・`*.stories.tsx`・`e2e/` の変更                                        | -    |
| 6   | コード品質・保守性 | コードの変更全般                                                                                        | ✅   |
| 7   | 要件適合性         | Issue 対応全般（受け入れ基準との照合）                                                                  | ✅   |

- 「常時」の観点は必ず実行する。それ以外は条件に合うときだけ実行する
- typo・コメント・ドキュメントだけの変更なら、コード品質も省いてよい（要件適合性のみ）

#### Step 2.5: レビューモードの判定

| 条件（上から順に判定）                                                                          | モード           |
| ----------------------------------------------------------------------------------------------- | ---------------- |
| `src/lib/dish.ts`・`src/lib/analyze-result.ts`・`next.config.ts` の変更がある（影響が広いため） | フルファンアウト |
| 変更が 400 行未満、かつ 8 ファイル未満（目安）                                                  | 統合モード       |
| それ以外                                                                                        | フルファンアウト |

- **フルファンアウト**: 選んだ観点ごとにサブエージェントを並列に起動する（観点 6・7 は 1 体にまとめる）
- **統合モード**: 1 体のサブエージェントに、選んだ観点をまとめて渡す。ただし**観点 1（セキュリティ）は該当するなら別に立てる**
- 行数は `git diff --stat` の末尾にある追加と削除の**合計**で数える。境界付近や影響の大きい変更はフルファンアウトに倒し、判定理由を一言残す

#### Step 3: 並列レビューの実行

選んだサブエージェントを**同じメッセージ内で並列に**起動する（`model: "sonnet"` を指定）。

委譲プロンプトに必ず含めるもの:

1. worktree の絶対パス
2. 変更ファイル一覧と **diff 本文**（400 行未満なら同梱。それ以上なら `git diff origin/$BASE_BRANCH` の実行を指示）
3. Issue 番号と受け入れ基準の要約
4. 下の「観点別の判定基準」「観点別のスコープ」の該当部分と、触れなくてよい観点
5. 出力形式: 各指摘に `[Critical|Major|Minor]` のラベルを付ける

サブエージェントが空の結果やエラーを返した場合、その観点はオーケストレーター自身が `git diff` と grep で直接レビューする（結果ゼロのまま集約に進まない）。

##### 委譲プロンプトのテンプレート（観点別）

```
あなたは{観点名}専門のレビュアーです。**{観点名}の観点だけ**に集中してレビューしてください。
他の観点（{除外する観点}）には触れないでください。

## 判定基準
{判定基準}

## スコープ（探索してよい範囲）
{観点別のスコープの該当行。許可された目的以外でコードベース全体を探索しない}

## 出力形式
各指摘を次のラベルで分類してください:
- [Critical] マージを止めるべき重大な問題（APIキーの漏えい、データの破壊、要件の未達）
- [Major] マージ前に直すべき問題（バグ、設計ルール違反、明らかな品質低下）
- [Minor] 改善の提案（スタイル、読みやすさ、軽い最適化）

指摘がない場合は「指摘なし」と書いてください。
確信が持てない指摘や軽い指摘も省略せずに報告してください（取捨選択は集約側で行います）。

## 変更内容
[変更ファイルの絶対パス。diff が 400 行未満なら本文も貼る]
```

##### 委譲プロンプトのテンプレート（統合モード）

```
あなたはコードレビュアーです。次の複数の観点を担当します。
**1 つの観点を最後まで終えてから次の観点に進んでください**（複数の観点を同時に斜め読みしない）。

## 担当する観点
{選んだ観点ごとに: 観点名 / 判定基準 / スコープ}

## 出力形式
観点ごとに見出しを分け、各指摘に [Critical|Major|Minor] と [観点名] のタグを付けてください。
指摘がない観点は「指摘なし」と書いてください。
確信が持てない指摘や軽い指摘も省略せずに報告してください。

## 変更内容
[変更ファイルの絶対パス + diff 本文]
```

##### 観点別の判定基準

1. **セキュリティ**: APIキーがログ・エラー応答・サーバーに残らないか（ログは `code` と処理時間だけ）、`src/lib/claude.ts` の `server-only`、Server Action 内での入力チェック（ファイル形式・サイズ・空白だけのキー）、CSP など `next.config.ts` のヘッダーを緩めていないか、ユーザー入力や Claude の応答をそのまま HTML に埋め込んでいないか
2. **アーキテクチャ**: `/dev:check-arch` の CRITICAL / WARNING 項目（階層の依存方向、atoms / molecules の禁止事項、Server Action を呼ぶのは pages 層だけ、`src/testing/` の import 禁止、templates は配置のみ）
3. **i18n**: 文言のハードコード（organisms 以上で `useTranslations` を使っているか）、`src/messages/*.json` の全ロケールでキーがそろっているか、ロケールの振り分け（`proxy.ts`）と `/[locale]` の静的生成を壊していないか
4. **パフォーマンス**: 不要な再レンダリング、`useEffect` の依存配列、画像の縮小処理の重さ、Client Component の範囲を広げすぎていないか（`"use client"` の位置）、バンドルサイズの増加、`/[locale]` が動的レンダリングに変わっていないか
5. **テスト品質**: 正常系・異常系・境界値の網羅、`expect(true).toBe(true)` のような無意味なアサーション、過剰なモック、フィクスチャへの影響漏れ、テスト名の明確さ、story の `play` が見た目ではなく振る舞いを検証しているか
6. **コード品質・保守性**: Rule of Three による重複、命名、`any` の使用、複雑さ、デッドコード、デザイントークンを使わない色の直書き
7. **要件適合性**: Issue の受け入れ基準を満たしているか、エッジケースの扱い、Issue 本文と実装の食い違い

##### 観点別のスコープ（探索の絞り方）

| 観点               | スコープ          | 許可する探索                                                                           |
| ------------------ | ----------------- | -------------------------------------------------------------------------------------- |
| セキュリティ       | diff + 限定探索   | `next.config.ts`・`src/lib/claude.ts`・`actions.ts` との比較（漏れは diff の外にある） |
| アーキテクチャ     | diff のみ         | なし（import 文とファイルパスで判定できる）                                            |
| i18n               | diff + 限定探索   | `src/messages/` の全ファイル、`src/i18n/`                                              |
| パフォーマンス     | diff + 限定探索   | diff から呼んでいる関数・フック・コンポーネントの実装                                  |
| テスト品質         | diff + 限定探索   | フィクスチャ・モック・`src/testing/` の横断 grep                                       |
| コード品質・保守性 | diff + 限定探索   | Rule of Three を判定するための類似コードの grep                                        |
| 要件適合性         | diff + Issue 本文 | エッジケースを確かめるための周辺コード                                                 |

#### Step 4: 結果の集約

全観点の結果を次の形でまとめる。同じ指摘は 1 つにまとめ、複数のレビュアーが挙げたものは優先して対応する。

```
## レビュー結果サマリー

### レビューモード
- 統合モード（変更: 5 ファイル / 180 行）／ フルファンアウト（理由: dish.ts の変更あり など）

### 実行した観点
- ✅ セキュリティ（理由: Server Action の入力チェックを変更）
- ⏭️ i18n（理由: messages の変更なし）
- ...

### 指摘の件数
- Critical: N 件 / Major: N 件 / Minor: N 件

### 詳細
[Critical] [観点] 指摘内容 → 対応方針
[Major]    [観点] 指摘内容 → 対応方針
[Minor]    [観点] 指摘内容 → 対応方針 or 見送る理由
```

#### Step 5: 修正と再レビュー

- **Critical / Major**: 必ず直す
- **Minor**: PR の本文に記載する。簡単に直せるものは直す
- 修正後は**影響を受けた観点だけ**再レビューする
- 修正でフルファンアウトの条件に新しく触れた場合や、変更量が統合モードの目安を超えた場合は、Step 2.5 からモードを判定し直す
- Critical / Major が 0 件になるまで繰り返す

### 5. プッシュ

```bash
git push -u origin feature/issue-$ISSUE_NUMBER
```

### 6. PR 作成前チェック

**`/pr:pre-pr-check` の手順に従う**（チェック項目と失敗時の対処はそちらが正）。コンフリクト確認は `origin/$BASE_BRANCH` に対して行う。すべて成功するまで次に進まない。

### 7. PR 作成

```bash
gh pr create --base $BASE_BRANCH --title "<type>: <English summary>" --body "$(cat <<'EOF'
## 概要
- [実装内容の要約]

## 関連 Issue
closes #$ISSUE_NUMBER

## 確認したこと
- [テスト項目]

## チェックリスト
- [x] テストを追加・更新した
- [x] Lint / フォーマット / 型チェックが通る
- [x] ビルドと E2E が通る
- [x] サブエージェントによる並列レビューが完了した

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

`$BASE_BRANCH` が `main` 以外の場合、PR をマージしても Issue は自動ではクローズされない（GitHub はデフォルトブランチへのマージでのみ自動クローズする）。その場合も `closes #$ISSUE_NUMBER` は残し、そのブランチが `main` にマージされたときにクローズされるようにする。

### 8. 完了報告

1. **実装サマリー**: 追加・変更したファイルの一覧と機能の概要
2. **PR の情報**: URL とタイトル
3. **テスト結果**: 追加したテストケースの数、カバレッジ（`/dev:coverage` で取れた場合）
4. **再委譲の回数**: 段階ごとの再委譲・エスカレーションの回数（0 回でも書く）
5. マージ後は `git worktree remove .claude/worktrees/issue-$ISSUE_NUMBER` で片付けられること

## 注意事項

- **動作確認は行わない**: ブラウザでの手動確認は省き、自動テスト（unit / browser / storybook / E2E）で品質を担保する
- **サブエージェントには必ず `model: "sonnet"` を指定する**
- レビューで Critical / Major が出たら必ず直す
- PR 作成前チェックでエラーが出たら必ず直してから PR を作る
- 小刻みにコミットする

## 通常版との違い

| 項目     | 通常版（`/issue:implement-issue`） | このコマンド（`/issue:implement-issue-auto`） |
| -------- | ---------------------------------- | --------------------------------------------- |
| worktree | 使う                               | 使う                                          |
| 動作確認 | ユーザーの手動確認を待つ           | 自動テストだけで品質を担保する                |
| 進め方   | 確認ポイントで止まる               | 最初から最後まで一気に進める                  |
| 実装者   | メインのセッション                 | サブエージェント（sonnet）                    |
| 用途     | 慎重に進めたい場合                 | 早く終わらせたい場合                          |
